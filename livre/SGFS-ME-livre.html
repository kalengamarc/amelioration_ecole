1. Avant-propos : apprendre par projet

1.1 Pourquoi ce livre existe

On apprend à nager dans l'eau, pas dans un manuel. En programmation, la piscine s'appelle un projet réel : du code imparfait, des contraintes de terrain, des choix à assumer, des bugs à traquer. SGFS-ME est exactement cela : une application utilisée par un complexe scolaire à Bujumbura pour encaisser des minervals, suivre des échéances et produire des reçus. Ce n'est pas un exercice de style.

Ce livre a donc une promesse simple : à la fin, vous serez capable de lire, modifier, déboguer et étendre cette application, et vous aurez acquis les gestes qui se transposent à n'importe quel logiciel de gestion.

1.2 Ce que « apprendre correctement » veut dire

Beaucoup de tutoriels apprennent à recopier. Nous visons autre chose, organisé en quatre niveaux :

  1. Lire — comprendre un fichier que vous n'avez pas écrit.
  2. Expliquer — dire pourquoi ce code est là, et ce qui casserait sans lui.
  3. Modifier — ajouter une fonctionnalité sans effet de bord.
  4. Concevoir — prendre une décision d'architecture et l'assumer.

Chaque chapitre travaille au moins deux de ces niveaux. Les exercices montent progressivement du niveau 1 au niveau 4.

🧠 La règle d'or du projet réel Ne demandez jamais « comment on écrit ça en React ? » avant de vous demander « que doit-il se passer métier ? ». Le code n'est que la conséquence d'une règle.

Exemple concret tiré du projet : un élève ne peut avoir qu'une seule inscription active. Cette phrase métier devient, au chapitre 12, un index SQL partiel :

CREATE UNIQUE INDEX IF NOT EXISTS idx_eleve_classe_one_active_per_eleve
ON EleveClasse(eleve_id) WHERE statut = 'ACTIF';

La base de données refuse une deuxième inscription active, même si un bug du front-end essaie d'en créer une. C'est ainsi qu'on écrit un logiciel fiable : la règle est inscrite au niveau le plus bas possible.

1.3 La méthode en cinq gestes

Pour chaque fonctionnalité du projet, appliquez cette séquence. Elle reviendra dans tous les chapitres.

Geste 1 — Nommer les objets du métier

Un logiciel de scolarité manipule : Etablissement, AnneeScolaire, Classe, Eleve, Tuteur, FraisScolaire, Echeance, Paiement, Depense, User, AuditLog. Ces noms sont ceux du code, du SQL et de l'interface. Cette homogénéité n'est pas un détail : elle réduit la charge mentale et évite les traductions approximatives.

Geste 2 — Dessiner le trajet de la donnée

Avant d'écrire une ligne :

Formulaire React → fonction tauri-commands → invoke('create_paiement')
→ commande Rust → validation → INSERT SQL → réponse JSON → toast + rafraîchissement

Si vous ne savez pas dessiner ce chemin, vous ne savez pas encore ce que vous codez.

Geste 3 — Écrire le plus petit code qui marche

Dans ce projet, chaque écran est un assemblage de briques existantes : un état local (useState), un appel de commande (tc.listEleves), une table, une boîte de dialogue. On n'invente une brique que lorsqu'aucune ne convient.

Geste 4 — Vérifier par l'observation

Lancez l'application, faites l'action, regardez la base :

# La base de développement sous Linux/macOS
ls ~/SGFS-ME/data/sgfs.db          # chemin réel utilisé par le code

Puis, avec sqlite3 (ou un outil graphique comme DB Browser for SQLite) :

SELECT numero_recu, montant, devise, annule FROM Paiement ORDER BY created_at DESC LIMIT 5;

Une base de données ne ment pas. C'est votre premier outil de débogage.

Geste 5 — Consigner ce qu'on a appris

Le dépôt contient worklog.md : un journal des tâches réalisées. Tenez le vôtre. Dans trois mois, vous aurez oublié pourquoi cette condition existe ; le journal, non.

⚠️ Piège réel du dépôt worklog.md contient actuellement un mot de passe en clair. Nous y revenons au chapitre 21 (exercice 21.2) : un secret ne doit jamais entrer dans un dépôt Git. Prenez l'habitude de relire vos journaux avant de committer.

1.5 Le contrat de lecture

Ce livre assume trois choses, et vous demande de les accepter :

  1. Le code du dépôt est la référence. Si le livre et le code divergent, le code gagne. Le livre explique pourquoi, le code dit comment.
  2. Tout n'est pas parfait. Le projet contient des dettes techniques assumées (sessions par identifiant, any par endroits, absence de tests automatisés). Les signaler et les corriger fait partie de l'apprentissage — c'est même le sujet des chapitres 19 à 22.
  3. On ne saute pas les erreurs. Les chapitres 2, 18 et 20 contiennent des listes d'incidents réels. Les lire vous fera gagner des heures.

1.7 Ce que vous saurez faire à la fin

  • Installer et lancer une application Tauri complète sur votre machine.
  • Expliquer chaque étape entre un clic et un enregistrement SQLite.
  • Écrire une commande Rust sécurisée (validation, transaction, audit).
  • Ajouter un écran CRUD en React/TypeScript en respectant le style du projet.
  • Diagnostiquer une synchronisation bloquée.
  • Construire un installateur et poser un plan de mise à jour des données.

2.2 Installer les dépendances

Ce que fait bun install : il lit package.json, résout les versions, écrit node_modules/. Les dépendances lourdes du projet, à connaître :

  • next, react, react-dom — le socle applicatif ;
  • zustand — l'état global ;
  • @tauri-apps/api — la passerelle IPC côté front ;

Côté Rust, les caisses sont déclarées dans src-tauri/Cargo.toml et récupérées au premier build par Cargo (quelques minutes, puis mis en cache).

2.3 Mode 1 : navigateur (bun run dev)

bun run dev      # next dev -p 3000

Next.js sert l'interface sur <http://localhost:3000>. Vous voyez la page d'accueil (src/components/page.tsx) puis l'écran de connexion.

⚠️ Ce mode n'a plus de back-end. L'historique du projet (worklog.md) indique que les routes src/app/api/* ont été supprimées lors de la migration vers Tauri. En navigateur, les appels passent par apiFetch, qui utilise fetch('/api/...')… et reçoit donc une 404. Enseignement : un front-end sans serveur ne peut pas lire une base locale. C'est précisément le problème que Tauri résout (chapitre 11). Le mode navigateur reste néanmoins utile pour travailler le CSS, la mise en page et les composants sans recompiler Rust.

2.4 Mode 2 : application de bureau (bun run tauri dev)

bun run tauri dev

Déroulement (défini dans src-tauri/tauri.conf.json) :

  1. Tauri lance npm run dev (beforeDevCommand) ;
  2. attend http://localhost:3000 (devUrl) ;
  3. compile le crate Rust (cargo build) ;
  4. ouvre une fenêtre WebView2 (Windows) / WebKitGTK (Linux) / WKWebView (macOS) qui charge cette URL ;
  5. dans cette WebView, window.__TAURI_INTERNALS__ existe → isTauri() renvoie true → apiFetch route vers invoke() au lieu de fetch().
// src/lib/store.ts
export function isTauri(): boolean {
  return typeof window !== 'undefined' && '__TAURI_INTERNALS__' in window
}

C'est la ligne qui sépare les deux mondes. Retenez-la.

2.5 Premier lancement : la base se crée toute seule

Au démarrage, lib.rs appelle db::init_db() :

.manage(db::init_db().expect("Failed to init database"))

init_db() (dans src-tauri/src/db/mod.rs) :

  1. ouvre (ou crée) le fichier sgfs.db dans le dossier de données utilisateur ;
  2. active journal_mode=WAL, busy_timeout=5000, foreign_keys=ON ;
  3. exécute le schéma SCHEMA (toutes les tables en CREATE TABLE IF NOT EXISTS) ;
  4. normalise les inscriptions actives, puis crée l'index unique partiel ;
  5. crée un administrateur par défaut si la table User est vide.

🔑 Premier identifiant : admin / admin123 (rôle COORDINATEUR). Changez-le immédiatement. Le chapitre 21 explique pourquoi ce mot de passe est un problème de sécurité en production.

Emplacement de la base (fonction get_db_path()) :

SystèmeChemin
Windows%APPDATA%\SGFS-ME\data\sgfs.db
Linux / macOS~/SGFS-ME/data/sgfs.db

🧠 Pourquoi pas le dossier de l'application ? Parce qu'un programme installé dans C:\Program Files n'a pas le droit d'écrire à côté de son exécutable. Les données utilisateur vont dans le profil de l'utilisateur. C'est une règle des systèmes d'exploitation modernes.

3. Le domaine métier : une école, des élèves, de l'argent

Avant le code, il faut comprendre le métier. Ce chapitre est le plus important du livre : tout le reste en découle. Prenez le temps de dessiner.

3.1 Le décor : un complexe scolaire, plusieurs écoles

SGFS-ME gère un réseau d'établissements. Un établissement possède un type :

TypeSignification
MATERNELLEpetite enfance
PRIMAIREécole primaire
SECONDAIREécole secondaire
COMPLEXEregroupe plusieurs niveaux

Chaque établissement a une devise (CDF, BIF, USD), une couleur principale (utilisée dynamiquement dans l'interface), un RCCM et un identifiant national. Ces deux derniers apparaissent sur les reçus officiels : ce ne sont pas des détails décoratifs.

🧠 Règle de conception n° 1 Un établissement n'est pas une « école » abstraite : c'est une unité comptable. Les paiements, les dépenses et les rapports sont toujours cloisonnés par établissement.

3.2 La chaîne de la scolarité

Etablissement
   └── AnneeScolaire  (« 2025-2026 », dates de début/fin, une seule active)
         └── Classe   (« 4e A », niveau, effectif max)
               └── EleveClasse  (l'élève X est inscrit dans la classe Y)
Eleve  ── TuteurEleve ──  Tuteur  (père, mère, tuteur légal)

L'année scolaire

L'année porte un libellé (2025-2026) et deux dates. Une seule année est active à la fois — c'est elle qui sert par défaut pour les nouvelles inscriptions.

⚠️ Piège vécu : si l'année active change en cours d'année, les frais et échéances déjà créés restent rattachés à l'ancienne année. C'est voulu : l'historique est immuable. Toutes les requêtes du projet filtrent donc explicitement par annee_scolaire_id (ou par active = 1 selon le contexte).

L'élève

ChampRemarque métier
matriculeunique, généré automatiquement (ELV-2026-0001) — il identifie l'élève à vie
nom, prenomle nom de famille d'abord, usage local
sexeM / F, sert aux statistiques
date_naissancesert au calcul de l'âge, contrôles d'admission
statutINSCRIT, ACTIF, SUSPENDU, TRANSFERE, DIPLOME
etablissement_idobligatoire : un élève appartient à un établissement

L'inscription à une classe

EleveClasse est une table de liaison enrichie : date_inscription, date_sortie, statut. Elle permet de garder l'historique des passages d'un élève dans les classes.

🧠 Règle de conception n° 2 — une seule inscription active par élève Un élève redoublant change de classe : on n'efface pas l'ancienne ligne, on la clôture (statut = 'TRANSFERE', date_sortie renseignée) et on en crée une nouvelle. La base l'impose par un index unique partiel (chapitre 12).

Les tuteurs

Tuteur est autonome (nom, prénom, téléphones, profession, relation). TuteurEleve lie un tuteur à un élève avec un drapeau is_principal. Le téléphone du tuteur est ce qu'on appelle lors d'un impayé : c'est une donnée critique dans la vraie vie. Le projet prévoit d'ailleurs des fonctions qui remontent le premier téléphone disponible (tuteur_phone_expr dans echeances.rs).

3.3 La chaîne financière : le cœur du logiciel

C'est ici que se joue la réputation du logiciel. Une école qui perd la trace d'un paiement perd la confiance des parents.

FraisScolaire  (Minerval T1 = 150 000 BIF, type SCOLARITE, pour la classe « 4e A »)
      │
      ├── FraisClasse   (quelles classes sont concernées)
      │
      ▼
Echeance  (1 par élève et par frais : montant_du, montant_paye, statut)
      ▲
      │  montant_affecte
Paiement  (reçu n° REC-20261024-0001, mode ESPECES, caisse de l'utilisateur)
      │
      └── AnnulationRecu  (si le reçu est annulé : motif, auteur, date)

Les frais

Un FraisScolaire a :

  • un libelle (« Minerval 1ère tranche »),
  • un type : SCOLARITE, INSCRIPTION, ANNEXE,
  • un montant et une devise (indépendante de celle de l'établissement !),
  • une annee_scolaire_id,
  • éventuellement une tranche et une date_echeance,
  • une liste de classes concernées (FraisClasse).

⚠️ Notion avancée mais essentielle Un frais peut être libellé en USD alors que l'école tient sa caisse en BIF. Le projet gère cela avec, sur le paiement, quatre champs : montant, devise, montant_affecte, devise_echeance, plus taux_change et montant_original. Autrement dit : le montant encaissé et le montant imputé à l'échéance ne sont pas forcément la même chose. Chapitre 14.

Les échéances

L'échéance matérialise « ce que cet élève doit pour ce frais ». Elle naît de la rencontre entre un frais et un élève. L'écran Échéances (echeances.rs) va plus loin : il agrège les échéances par élève, calcule le dû, le payé, le reste, le retard en jours, et produit un message de relance lisible (« Minerval T1 : 50 000 BIF restant »).

Statuts calculés :

ConditionStatut affiché
total_paye >= total_duPAYE
0 < total_paye < total_duPARTIELLEMENT_PAYE
total_paye <= 0EN_ATTENTE (ou EN_RETARD si date dépassée)

🧠 Règle de conception n° 3 — l'échéance est un solde, pas un reçu Un paiement partiel ne crée pas une nouvelle échéance : il incrémente montant_paye. L'historique financier est porté par Paiement, l'état courant par Echeance. Ne mélangez jamais les deux rôles.

Les paiements

Champs à connaître par cœur :

id, numero_recu (unique), eleve_id, echeance_id (nullable),
etablissement_id, annee_scolaire_id, user_id (le caissier),
motif, montant, devise, montant_affecte, devise_echeance,
mode_paiement, reference_paiement, taux_change, montant_original,
annule, date_annulation, created_at, updated_at

Deux points de vigilance :

  1. echeance_id est nullable : on peut encaisser un paiement « global » (plusieurs frais d'un coup). L'imputation se fait alors dans le calcul (voir LigneFrais).
  2. annule remplace la suppression : on n'efface jamais un reçu (obligation comptable). On l'annule, avec un motif conservé dans AnnulationRecu.

Les dépenses

Depense enregistre les sorties : salaires, fournitures, loyer, entretien… Champs : categorie, libelle, montant, devise, beneficiaire, date_depense, reference_piece, justificatif_url, statut (VALIDE par défaut).

🧠 Règle de conception n° 4 — recettes et dépenses ne se mélangent pas Le bénéfice est calculé devise par devise (dashboard.rs), jamais en additionnant des francs congolais et des dollars. Le code construit un BTreeMap<String, f64> par devise, puis soustrait. C'est une décision de comptabilité, pas de programmation.

  if (!role) return true            // ⚠️ permissif par défaut

3.5 Les règles métier à ne jamais violer

Voici la « constitution » du projet. Affichez-la au-dessus de votre écran.

  1. Un paiement n'est jamais supprimé, seulement annulé, avec motif et auteur.
  2. Le montant payé d'une échéance ne peut pas être négatif (MAX(0, …) dans le code).
  3. Un élève n'a qu'une inscription active.
  4. Un matricule est unique et ne change pas.
  5. Les totaux ne s'additionnent jamais entre devises.
  6. Toute opération sensible est journalisée dans AuditLog.
  7. Un reçu porte un numéro unique et séquentiel par jour (REC-AAAAMMJJ-0001).
  8. Les données ne sont jamais perdues en cas de coupure réseau : SQLite d'abord, cloud ensuite (chapitre 17).

Étape 2 — La passerelle traduit en appel IPC

src/lib/tauri-commands.ts est la couche de traduction. Elle :

  • renomme les paramètres en snake_case attendu par Rust (eleve_id, …) ;
  • appelle invoke() ;
  • déballe la réponse et lève une erreur si success === false ;
  • signale aux autres composants qu'une écriture a eu lieu.
function unwrap<T>(res: any): T {
  if (res && res.success === false) throw new Error(res.error || 'Erreur inconnue')
  return res as T
}

async function cmd<T = any>(command: string, params: Record<string, any> = {}): Promise<T> {
  const result = unwrap<T>(await invoke(command, params))
  const isLocalWrite = /^(create|update|delete|save|activer|annuler|clean)_/.test(command)
    && !command.startsWith('sync_') && command !== 'save_sync_config'
  if (isLocalWrite && typeof window !== 'undefined') {
    window.dispatchEvent(new Event('local-data-changed'))
  }
  return result
}

Ce détail est élégant : une seule règle suffit à déclencher la synchronisation automatique après toute écriture locale (chapitre 17).

5.3 page.tsx : le chef d'orchestre

src/app/page.tsx est un composant client ('use client') qui décide de tout : accueil, connexion, ou application. Sa logique tient en quatre blocs.

Bloc 1 — session au démarrage

useEffect(() => {
  async function checkSession() {
    try {
      const token = getStoredAuthToken()
      if (!token) { useAppStore.getState().logout(); setLoading(false); return }
      const data = await tc.getMe(token)
      if (data.success && data.data) useAppStore.getState().login(data.data, token)
      else useAppStore.getState().logout()
    } catch {
      useAppStore.getState().logout()
    } finally {
      setLoading(false)
    }
  }
  checkSession()
}, [])

Trois principes ici :

  1. useEffect(…, []) = « au montage seulement ».
  2. On vérifie le jeton auprès du back-end : un localStorage peut être périmé.
  3. finally garantit que l'écran de chargement disparaît, même en cas d'erreur.

⚠️ data.success && data.data — le back-end renvoie {success:true, data:{…}}. Si vous changez ce contrat côté Rust, tous les écrans se cassent silencieusement. C'est le type de couplage qu'il faut documenter (voir chapitre 11).

Bloc 2 — contexte de l'établissement

useEffect(() => {
  if (!isAuthenticated || !user || etablissements.length === 0) return

  let targetId: string | undefined
  if (user.role === 'COORDINATEUR') {
    targetId = etablissements.find((e: any) => e.actif !== false)?.id
  } else {
    targetId = user.etablissementId || undefined
  }
  if (!targetId) return

  tc.getEtablissementContext(targetId)
    .then((data: any) => {
      if (data.success && data.data) {
        setCurrentEtablissement(data.data.etablissement)
        setEtabParams(data.data.parametres ?? null)
      }
    })
    .catch(() => {})
}, [isAuthenticated, user, etablissements])

Ici se joue une règle métier : le coordonnateur voit toutes les écoles, un secrétaire est verrouillé sur la sienne. On retrouve cette logique dans chaque écran via getSchoolFilter.

Bloc 3 — synchronisation automatique

const initialTimer = setTimeout(runAutoSync, 30000)          // 30 s après connexion
const interval = setInterval(runAutoSync, 5 * 60 * 1000)     // toutes les 5 min
window.addEventListener('local-data-changed', scheduleAfterChange) // 5 s après écriture
window.addEventListener('online', runAutoSync)

return () => {
  clearTimeout(initialTimer)
  clearInterval(interval)
  if (changeTimer) clearTimeout(changeTimer)
  window.removeEventListener('local-data-changed', scheduleAfterChange)
  window.removeEventListener('online', runAutoSync)
}

🧠 Le nettoyage d'effet n'est pas optionnel. Sans le return, chaque re-connexion empile un nouvel intervalle : la synchronisation partirait 5, 10, 15 fois par minute. C'est le bug React le plus courant en production.

Le « debounce » de 5 secondes est une décision produit : trois écritures rapides (élève + tuteur + inscription) ne déclenchent qu'une synchronisation.

Bloc 4 — rendu conditionnel

if (loading) return <ÉcranDeChargement />
if (!isAuthenticated) return showLogin ? <LoginPage /> : <Accueil />

const renderPage = () => {
  switch (currentPage) {
    case 'dashboard':     return <DashboardPage />
    case 'eleves':        return <ElevesPage />
    case 'encaissements': return <EncaissementsPage />
    // …
    default:              return <DashboardPage />
  }
}

Deux styles de navigation coexistent : un switch sur currentPage (état Zustand) et un routage Next.js absent. C'est un choix : une application de bureau à fenêtre unique n'a pas besoin d'URL. Avantage : simplicité et état conservé. Inconvénient : pas de lien profond, pas de bouton « retour ».

5.7 'use client' : pourquoi partout ?

En Next.js 14, les composants sont des Server Components par défaut. Comme l'export est statique et que tout tourne dans la WebView, chaque composant qui utilise un état, un effet ou un gestionnaire d'événement doit déclarer :

'use client'

Symptômes d'un oubli :

  • écran vide lors du build statique.

6. TypeScript solide

TypeScript n'est pas là pour « faire joli ». Dans un projet qui manipule de l'argent, c'est un garde-fou. Ce chapitre montre comment le dépôt l'utilise — et où il cède du terrain.

6.1 Configuration

6.3 Unions, littéraux et objets de correspondance

Le projet préfère as const + objet de correspondance aux enum :

export const ETAB_TYPES = ['MATERNELLE', 'PRIMAIRE', 'SECONDAIRE', 'COMPLEXE'] as const

    PRIMAIRE: 'Primaire',

    COMPLEXE: 'Complexe',

  return labels[type] || type

Record<string, string> = « dictionnaire clé/texte ». Pour un libellé de statut on préfère stocker le style avec le texte :

const STATUS_LABEL: Record<string, { label: string; className: string }> = {
  ACTIF:     { label: 'Actif',     className: 'bg-emerald-100 text-emerald-800 …' },

}

Ainsi, ajouter un statut = ajouter une ligne, sans toucher au rendu. C'est un petit patron de conception : données plutôt que conditions.

6.5 Le pattern défensif des réponses

Le back-end n'a pas toujours renvoyé la même forme. Résultat, les écrans pratiquent :

const res = await tc.listClasses(etabId, year)
const data = res?.classes ?? res?.data ?? []

Décortiquons :

?? res?.dataforme {data:[…]} (api_response)
?? []aucune des deux : on affiche une liste vide
Array.isArrayce n'est pas un tableau ? on évite le crash

🧠 C'est de la programmation défensive sur un contrat instable. Utile, mais ce n'est pas une solution : la vraie correction est d'uniformiser les réponses côté Rust (exercice 6.2).

6.6 Narrowing et garde-fous

// src/lib/store.ts
export function isCoordinateur(role: string | null | undefined): boolean {
  if (!role) return true
  const r = role.toUpperCase()
  return r === 'COORDINATEUR' || r === 'ADMIN' || r === 'SUPERADMIN'
      || r === 'ADMINISTRATEUR' || r === 'COORD'
}

TypeScript apprend ici que role est une string après le if (!role) return. C'est le narrowing (rétrécissement de type).

// Extraction d'un objet imbriqué, avec repli
const t = s.tuteurs?.find((x: any) => x.tuteur?.isPrincipal)?.tuteur
       ?? s.tuteurs?.[0]?.tuteur

Chaque ?. évite un Cannot read properties of undefined.

⚠️ Piège de logique : isCoordinateur renvoie true quand role est vide. « Pas d'information » devient « tous les droits ». C'est une faille par défaut permissif (fail-open). Un système financier doit échouer fermé (return false). Notez-le pour l'exercice 21.1.

6.7 Typer une commande Tauri

export async function login(username: string, password: string) {

Le paramètre req est un objet imbriqué : la commande Rust attend req: LoginRequest, avec username / password en snake_case-compatible (pas de renommage ici). Voir tauri-commands.ts pour les variantes (etablissementId et etablissement_id envoyés ensemble — un bricolage de compatibilité assumé).

7. État global avec Zustand

7.1 Pourquoi un état global ?

Une application de bureau a besoin de données partagées par tous les écrans :

  • l'utilisateur connecté et son jeton ;
  • la page courante ;
  • l'établissement sélectionné (sa couleur, sa devise, son nom) ;
  • les paramètres de cet établissement (pied de page des reçus, imprimante).

Les faire descendre de composant en composant (« prop drilling ») serait pénible. Zustand offre un magasin simple, sans Provider, avec persistance intégrée.

7.2 Le magasin du projet

// src/lib/store.ts
interface AppState {
  // Auth
  user: UserInfo | null
  token: string | null
  isAuthenticated: boolean
  login: (user: UserInfo, token: string) => void
  logout: () => void

  // Navigation
  currentPage: PageName
  setPage: (page: PageName) => void
  sidebarOpen: boolean
  setSidebarOpen: (open: boolean) => void
  toggleSidebar: () => void

  // Contexte établissement
  currentEtablissement: EtablissementContext | null
  setCurrentEtablissement: (etab: EtablissementContext | null) => void
  etabParams: EtabParams | null
  setEtabParams: (params: EtabParams | null) => void
}

export const useAppStore = create<AppState>()(
  persist(
    (set) => ({
      user: null,
      token: null,
      isAuthenticated: false,
      login: (user, token) => set({ user, token, isAuthenticated: true }),
      logout: () => set({
        user: null, token: null, isAuthenticated: false,
        currentEtablissement: null, etabParams: null,
      }),

      currentPage: 'dashboard',
      setPage: (page) => set({ currentPage: page }),
      sidebarOpen: true,
      setSidebarOpen: (open) => set({ sidebarOpen: open }),
      toggleSidebar: () => set((s) => ({ sidebarOpen: !s.sidebarOpen })),

      currentEtablissement: null,
      setCurrentEtablissement: (etab) => set({ currentEtablissement: etab }),
      etabParams: null,
      setEtabParams: (params) => set({ etabParams: params }),
    }),
    {
      name: 'sgfs-storage',
      partialize: (state) => ({
        token: state.token,
        user: state.user,
        isAuthenticated: state.isAuthenticated,
      }),
    }
  )
)

Trois détails qui comptent

  1. partialize : seule la session est persistée. On ne veut pas retrouver la page « paramètres » ou une sidebar fermée au prochain démarrage — et surtout pas des données métier périmées.
  2. Le nom sgfs-storage est le contrat avec le passé : le changer déconnecte tous les utilisateurs existants.
  3. set((s) => ({...})) : forme fonctionnelle quand la nouvelle valeur dépend de l'ancienne.

🧠 Sécurité : persist écrit le jeton dans localStorage de la WebView. C'est acceptable pour une application locale mono-utilisateur, pas pour un site public (vulnérable au XSS). Le chapitre 21 en reparle.

7.3 Lire le magasin dans un composant

const { user, currentPage } = useAppStore()

Attention : cette écriture s'abonne à tout le magasin. Chaque changement de sidebarOpen re-rend l'écran. La forme recommandée est le sélecteur :

const user = useAppStore((s) => s.user)
const setPage = useAppStore((s) => s.setPage)

7.8 Persistance, versionnage et migration

Aujourd'hui, persist n'a pas de version. Si la forme de UserInfo change (par exemple etablissementId devient etablissements: string[]), les anciennes sessions seront désérialisées dans une forme incompatible.

Solution robuste :

persist(store, {
  name: 'sgfs-storage',
  version: 2,
  migrate: (persisted: any, version) => {
    if (version < 2) {
      persisted.user = { ...persisted.user, etablissements: persisted.user.etablissementId ? [persisted.user.etablissementId] : [] }
    }
    return persisted
  },
  partialize: (s) => ({ token: s.token, user: s.user, isAuthenticated: s.isAuthenticated }),
})

8.3 Étape 2 — Le chargement

const fetchStudents = useCallback(async () => {
  if (!user) return
  setLoading(true)
  try {
    const sf = getSchoolFilter(role, userEtabId)
    const etabId = sf || school || undefined

    const res = await tc.listEleves({
      etablissementId: etabId,
      anneeScolaireId: year || undefined,
      classeId: classe || undefined,
      search: search || undefined,
      page,
      pageSize: 15,
    })

    let students = res?.data ?? []
    if (filterNoClass) {
      students = students.filter((s: Student) => {
        const inscriptions = s.inscriptions || s.classes || []
        return !inscriptions.some((x: any) =>
          x.statut === 'ACTIF' && (x.classe_id || x.classe?.id))
      })
    }
    setStudents(students)
    setTotal(filterNoClass ? students.length : (res?.pagination?.total ?? 0))
    setTotalPages(filterNoClass ? Math.ceil(students.length / 15) : (res?.pagination?.totalPages ?? 1))
  } catch (e: any) {
    toast.error(e?.message || 'Erreur chargement')
  } finally {
    setLoading(false)
  }
}, [user, role, userEtabId, school, year, classe, search, page, filterNoClass])

À observer :

  • un seul point d'entrée réseau par liste (pas d'appel dispersé dans le JSX) ;
  • setLoading(true) avant, false dans finally : jamais de spinner bloqué ;
  • les filtres vides deviennent undefined, pas '' (côté Rust, '' est une valeur, pas une absence) ;
  • le filtre « sans classe » est appliqué côté client — acceptable car la page ne contient que 15 lignes, mais faux sur une grosse pagination (exercice 8.2).

⚠️ Défaut réel : quand filterNoClass est actif, on filtre après pagination. Les compteurs deviennent approximatifs. La bonne solution est un paramètre sansClasse=true traité par list_eleves en SQL.

8.4 Étape 3 — Déclencher sans boucler

useEffect(() => { fetchYears() }, [fetchYears])

useEffect(() => { fetchStudents() }, [fetchStudents])

Chaque fonction de chargement a un effet qui la déclenche. Quand un filtre change, la fonction change (nouvelle identité useCallback), l'effet se relance : le rechargement est automatique, sans écrire onChange={… fetch()} partout.

🧠 Pensez « l'état pilote, l'effet suit ». C'est le renversement qui rend React prévisible.

8.6 Étape 5 — Enregistrer

async function handleSave() {
  // validation…
  setBusy(true)
  const payload = {
    nom: form.nom.trim(), prenom: form.prenom.trim(), sexe: form.sexe,
    dateNaissance: form.dateNaissance || undefined,
    lieuNaissance: form.lieuNaissance || undefined,
    etablissementId: form.etablissementId,
    anneeScolaireId: form.anneeScolaireId,
    classeId: form.classeId,
    tuteurs: form.tuteurNom.trim() && form.tuteurPrenom.trim() ? [{
      nom: form.tuteurNom.trim(), prenom: form.tuteurPrenom.trim(),
      telephone: form.tuteurTelephone.trim() || 'Non renseigné',
      relation: form.tuteurRelation,
      profession: form.tuteurProfession || undefined,
      isPrincipal: true,
    }] : [],
  }

  try {
    if (editingId) {
      await tc.updateEleve(editingId, payload)
      toast.success('Élève modifié avec succès')
    } else {
      await tc.createEleve(payload)
      toast.success('Élève inscrit avec succès')
    }
    setFormOpen(false)
    fetchStudents()
  } catch (e: any) {
    toast.error(typeof e === 'string' ? e : e?.message || 'Erreur inconnue')
  } finally {
    setBusy(false)
  }
}

Les cinq gestes du « save » réussi :

  1. désactiver le bouton (busy) pour éviter le double envoi ;
  2. envoyer des données nettoyées (trim(), vides → undefined) ;
  3. fermer le dialogue après le succès seulement ;
  4. recharger la liste (ou insérer le résultat dans l'état) ;
  5. notifier l'utilisateur.

🧠 Pourquoi recharger plutôt qu'insérer localement ? Parce que le back-end enrichit la réponse (matricule généré, classe jointe, statut). Recharger garantit la cohérence, au prix d'un aller-retour local — négligeable en SQLite.

10.3 Option et Result : les deux types qui changent tout

Option<T> remplace null

    pub id: String,
    pub etablissement_id: Option<String>,   // peut être absent

}

Utilisation :

Équivalent JS : user.etablissementId ?? null. La différence : le compilateur vous force à traiter le cas None.

Result<T, E> remplace les exceptions

#[tauri::command]
pub fn get_eleve(db: State<'_, DbConn>, id: String) -> Result<serde_json::Value, AppError> {
    let conn = db.lock()?;              // le ? remonte l'erreur
    let eleve = conn.query_row("SELECT … WHERE id = ?", params![id], |r| { … })?;
    Ok(api_response(Ok(eleve)))
}

? = « si erreur, retourne-la immédiatement ; sinon, récupère la valeur ». C'est un try/catch mais visible dans la signature. Le front reçoit alors le message d'erreur.

Le type d'erreur du projet

11. Tauri : commandes, IPC, permissions

11.1 Qu'est-ce que Tauri ?

Tauri assemble trois choses :

  1. une WebView (le navigateur du système) qui affiche le front-end ;
  2. un cœur Rust compilé, qui possède les fichiers, la base, le réseau ;
  3. un pont IPC (appels de procédure inter-processus) entre les deux.

Comparé à Electron, Tauri n'embarque pas Chromium : l'application pèse quelques mégaoctets et non 150. Le prix : les WebView diffèrent selon l'OS (WebView2 sur Windows, WebKitGTK sur Linux), donc testez sur chaque cible.

11.2 Anatomie d'une commande

#[tauri::command]
pub fn get_eleve(
    db: State<'_, DbConn>,
    id: String,
) -> Result<serde_json::Value, AppError> { … }

Règles :

  • #[tauri::command] génère le code d'exposition IPC ;
  • les paramètres doivent être désérialisables (types simples ou struct Deserialize) ;
  • le nom des paramètres est celui attendu côté JS en camelCase par défaut (eleve_id côté Rust ⇒ eleveId côté JS) ;
  • le type de retour doit être Serialize (ou Result<_, E> avec E: Serialize).

Côté JavaScript :

import { invoke } from '@tauri-apps/api/core'
await invoke('get_eleve', { id: 'abc-123' })

11.3 Le pont du projet : tauri-commands.ts

Le fichier compte 707 lignes et 57 fonctions. Il joue trois rôles.

Rôle 1 — Déballer la réponse

function unwrap<T>(res: any): T {
  if (res && res.success === false) throw new Error(res.error || 'Erreur inconnue')
  return res as T
}

Le back-end renvoie toujours {success, data|error} ; sans unwrap, chaque écran devrait tester success. Une fois, au bon endroit.

Rôle 2 — Traduire les noms

export async function createFrais(data: Record<string, any>) {
  return cmd('create_frais', { …data })
}

Les fonctions explicites documentent les paramètres réellement attendus. Certaines envoient deux orthographes :

export async function listAnneesScolaires(etablissementId?: string) {
  const etabId = etablissementId || null
  return cmd('list_annees_scolaires', {
    etablissementId: etabId,
    etablissement_id: etabId,   // compatibilité ascendante
  })
}

C'est un pansement : Tauri convertit automatiquement camelCase → snake_case, donc un seul nom suffit normalement. On garde les deux par prudence historique.

Rôle 3 — Signaler les écritures

const isLocalWrite = /^(create|update|delete|save|activer|annuler|clean)_/.test(command)
  && !command.startsWith('sync_') && command !== 'save_sync_config'

if (isLocalWrite && typeof window !== 'undefined') {
  window.dispatchEvent(new Event('local-data-changed'))
}

Une convention de nommage devient un comportement applicatif. Conséquence : nommer une commande set_something casserait la synchronisation automatique. Documentez ce genre de règle implicite.

11.5 Les permissions de la fenêtre

Tauri 2 utilise un système de capacités : par défaut, la WebView n'a accès à rien hors core:default. Chaque plugin doit être autorisé (shell:allow-open autorise l'ouverture d'URL/fichiers via le plugin shell).

⚠️ Deux anomalies à connaître

  1. Le JSON contient deux blocs identifier/permissions dans le même objet : les clés dupliquées sont écrasées silencieusement par le parseur. Résultat fragile.
  2. La CSP est désactivée ("csp": null) dans tauri.conf.json. Acceptable en développement, à durcir en production.

"security": {
  "csp": "default-src 'self'; img-src 'self' asset: data: blob:; style-src 'self' 'unsafe-inline'; connect-src 'self' https://*.supabase.co"
}

11.6 invoke est-il sûr ?

Les commandes sont accessibles à tout code JavaScript exécuté dans la WebView. Si une faille XSS existe (par exemple un nom d'élève injecté dans le DOM), un attaquant pourrait appeler delete_etablissement. Conséquences :

  • toute validation critique doit être côté Rust ;
  • ne jamais construire de SQL par concaténation de chaînes (voir chapitre 12) ;
  • assainir les contenus affichés (React échappe par défaut : n'utilisez pas dangerouslySetInnerHTML) ;
  • vérifier l'identité de l'appelant sur les commandes sensibles (chapitre 21).

12.3 Les index : la performance écrite à la main

CREATE INDEX IF NOT EXISTS idx_echeance_eleve_statut ON Echeance(eleve_id, statut);
CREATE INDEX IF NOT EXISTS idx_paiement_etab_date     ON Paiement(etablissement_id, created_at);
CREATE INDEX IF NOT EXISTS idx_eleve_nom_prenom       ON Eleve(nom, prenom);

Un index est comme l'index d'un livre : il évite de parcourir toutes les pages. Règles :

  • indexez les colonnes utilisées dans WHERE, JOIN, ORDER BY ;
  • l'ordre des colonnes compte : (etablissement_id, created_at) sert à filtrer par école puis trier par date ;
  • trop d'index ralentissent les écritures.

L'index unique partiel : une règle métier en SQL

CREATE UNIQUE INDEX IF NOT EXISTS idx_eleve_classe_one_active_per_eleve
ON EleveClasse(eleve_id) WHERE statut = 'ACTIF';

Traduction : « au plus une ligne ACTIF par élève ». C'est la règle du chapitre 3, imposée par la base. Avant de créer cet index, init_db normalise les doublons :

fn normalize_active_enrollments(conn: &Connection) -> Result<(), AppError> {
    conn.execute(
        "UPDATE EleveClasse SET statut = 'TRANSFERE', date_sortie = ?
         WHERE statut = 'ACTIF'
           AND EXISTS (SELECT 1 FROM EleveClasse AS kept
                       WHERE kept.eleve_id = EleveClasse.eleve_id
                         AND kept.statut = 'ACTIF'
                         AND (kept.date_inscription > EleveClasse.date_inscription
                              OR (kept.date_inscription = EleveClasse.date_inscription
                                  AND kept.classe_id > EleveClasse.classe_id)))",
        rusqlite::params![now],
    )?;
    Ok(())
}

🧠 Migration de données avant contrainte : c'est un patron classique. On répare l'existant, puis on verrouille. Faire l'inverse échoue sur les bases déjà polluées.

  1. une base installée chez un client est immuable sans migration ; le code doit gérer plusieurs générations de schéma ;
  2. cette complexité coûte cher (le fichier echeances.rs fait 1 130 lignes) ;
  3. la solution propre est un système de migrations versionnées (exercice 20.3).

⚠️ Constat à corriger : supabase_schema.sql et le schéma local ne sont pas alignés (types, colonnes, contraintes). Toute synchronisation peut échouer sur un champ absent. C'est la source des erreurs du chapitre 18.

12.5 Écrire du SQL en Rust, sans injection

La bonne manière : les paramètres liés

La mauvaise manière

Le cas difficile : les filtres dynamiques

12.6 Transactions : tout ou rien

Le projet fait souvent plusieurs écritures successives. Exemple create_eleve :

INSERT Eleve → INSERT EleveClasse → INSERT Tuteur → INSERT TuteurEleve

Si la troisième requête échoue, l'élève existe sans tuteur : données partielles. La solution est la transaction :

let tx = conn.transaction()?;                 // nécessite conn: &mut Connection
tx.execute("INSERT INTO Eleve …", params![…])?;
tx.execute("INSERT INTO EleveClasse …", params![…])?;
tx.commit()?;                                  // rien n'est écrit avant cette ligne

En cas d'erreur, tx est abandonné (rollback implicite).

Adapter le projet

DbConn est Mutex<Connection>. Pour obtenir un &mut Connection, il faut verrouiller en mutable :

let mut conn = db.lock()?;
let tx = conn.transaction()?;

🔧 Exercice 13.3 — Transformez create_eleve et create_paiement en transactions. Testez en provoquant volontairement une erreur au milieu (par exemple un matricule dupliqué) : aucune ligne ne doit rester.

12.10 À retenir

  • SQLite : zéro installation, hors-ligne, un fichier — idéal pour le terrain.

13. Une commande de bout en bout

Ce chapitre est un guide de réalisation. Objectif : écrire (ou réécrire proprement) une commande complète, depuis le bouton jusqu'à la ligne SQLite.

Nous prenons create_paiement, la commande la plus sensible du projet.

13.1 Le cahier des charges

Encaisser un paiement : étant donné un élève, éventuellement une échéance, un montant, une devise et un caissier, créer un reçu numéroté, mettre à jour l'échéance, journaliser l'opération, renvoyer le reçu complet.

Contraintes métier :

  1. l'élève doit exister et être actif dans un établissement actif ;
  2. le montant doit être strictement positif ;
  3. le reçu doit porter un numéro unique ;
  4. l'échéance, si fournie, doit appartenir au même élève ;
  5. le montant payé de l'échéance ne doit pas dépasser le dû (ou l'excédent doit être signalé) ;
  6. l'opération doit être atomique ;
  7. elle doit être auditée.

14. Argent, devises et arrondis

C'est le chapitre qui distingue un logiciel amateur d'un logiciel professionnel. Une école burundaise encaisse en francs burundais (BIF), parfois en francs congolais (CDF), parfois en dollars (USD). Les frais peuvent être libellés dans une devise et payés dans une autre.

14.1 Le piège des nombres à virgule flottante

En JavaScript et en Rust, f64 est un binaire à virgule flottante :

0.1 + 0.2            // 0.30000000000000004
(1.005).toFixed(2)   // "1.00"  ← arrondi faux
0.1 * 3 === 0.3      // false

En comptabilité, ces écarts s'accumulent et deviennent visibles sur un reçu.

Trois stratégies :

StratégiePrécisionEffortUsage
f64 + tolérance (0,01)acceptablefaibleétat actuel du projet
entiers (centimes)exactemoyenrecommandé à terme
decimal (bigdecimal)exacteélevébanques

🧠 Le BIF n'a pas de centimes en pratique : les montants sont des entiers. Cette particularité sauve le projet… tant que personne ne saisit de décimales.

for m in &depenses     { acc.entry(m.devise.clone()).or_insert((0.0, 0.0)).1 += m.total; }

Si un total consolidé est indispensable à l'affichage, convertissez explicitement avec un taux daté et affichez la mention « équivalent USD au taux du … ».

14.5 Arrondis : où et comment

Trois moments d'arrondi :

  1. à la saisie — on accepte ce que le caissier tape, avec deux décimales maximum ;
  2. au calcul (conversion) — arrondi au centime ;
  3. à l'affichage — maximumFractionDigits selon la devise.

Règles pratiques :

// Arrondi « banquier » évite les biais statistiques sur de gros volumes
function round2(n: number): number {
  return Math.round((n + Number.EPSILON) * 100) / 100
}

et en Rust :

let arrondi = (montant * 100.0).round() / 100.0;

🧠 Gardez toujours la valeur non arrondie en base et arrondissez à l'affichage : arrondir puis re-arrondir crée des écarts de caisse.

La tolérance du projet

let nouveau = paye + affecte;
if nouveau > du + 0.01 { /* dépassement */ }

0.01 est une tolérance, pas une égalité. Justifiez-la en commentaire.

14.6 Cas pratiques à traiter correctement

Cas 1 — Paiement partiel

Dû 150 000, payé 50 000 → montant_paye = 50000, statut PARTIELLEMENT_PAYE. Le reçu indique « Reste à payer : 100 000 BIF ». Le reçu doit porter cette mention : c'est ce qui évite les contestations.

Cas 2 — Trop-perçu

Un parent paie 160 000 pour 150 000. Deux politiques possibles :

  • refuser (le plus simple, le plus sûr) ;
  • accepter et créditer (nécessite un champ d'avoir ou de crédit élève).

Le code actuel ne contrôle pas : c'est un bug (exercice 14.3). Si vous choisissez le crédit, créez une table CreditEleve et imputez-le lors du prochain frais.

Cas 3 — Annulation

Annuler un paiement doit décrémenter l'échéance :

"UPDATE Echeance SET montant_paye = MAX(0, montant_paye - ?), updated_at = ? WHERE id = ?"

Le MAX(0, …) protège contre un solde négatif si les données sont incohérentes.

Cas 4 — Changement de taux en cours d'année

Le taux ParametreEtablissement.taux_change_usd_bif peut évoluer. Ne recalculez pas les paiements passés : chaque paiement stocke son taux (taux_change). C'est la bonne pratique comptable : un historique ne se réécrit pas.

L'écriture

// src-tauri/src/utils/audit_logger.rs
pub fn log_audit(
    conn: &std::sync::Mutex<rusqlite::Connection>,
    user_id: Option<&str>,
    action: &str,
    entite: &str,
    entite_id: Option<&str>,
    details: Option<&str>,
) {
    let id = generate_id();
    let now = crate::db::now_iso();
    let Ok(conn) = conn.lock() else { return };
    let _ = conn.execute(
        "INSERT INTO AuditLog (id, user_id, action, entite, entite_id, details, created_at)
         VALUES (?1,?2,?3,?4,?5,?6,?7)",
        params![id, user_id, action, entite, entite_id, details, now],
    );
    // Rétention : conserver les 200 entrées les plus récentes
    let _ = conn.execute(
        "DELETE FROM AuditLog WHERE id NOT IN
         (SELECT id FROM AuditLog ORDER BY created_at DESC LIMIT 200)", []);
}

Trois problèmes à voir

  1. Rétention à 200 lignes. Sur une école qui encaisse 100 paiements par jour, cela représente deux jours d'historique. Un audit financier exige des années. Il faut une politique de conservation par date (par exemple 5 ans) et une purge archivable.
  2. user_id souvent None. Beaucoup d'appels passent None (voir create_eleve : log_audit(&db, None, "CREATE", …)). Résultat : impossible de savoir qui a inscrit l'élève. L'identité de l'appelant doit remonter, soit par paramètre, soit par un mécanisme de session côté Rust.
  3. let _ = avale les erreurs. Si l'insertion échoue, personne ne le saura. Pour un journal d'audit, c'est discutable : mieux vaut tracer sur stderr au minimum.

🧠 Un journal d'audit n'est pas un journal de débogage. Il est immuable, horodaté, attribué, et ne contient aucune donnée sensible en clair (pas de mot de passe, pas de numéro de carte).

16. Tableau de bord et rapports

16.1 À quoi sert un tableau de bord ?

Un directeur ne lit pas des tables. Il veut trois réponses en dix secondes :

16.3 La dette : le calcul le plus délicat

Le commentaire du code est explicite :

/* ── Dette par devise ───────────────────────────────────────────
 * Agrégation en trois passes :
 *   A. échéances matérialisées, devise du frais
 *   B. repli FraisScolaire pour les élèves sans échéance
 *   C. correction si Paiement montre plus que Echeance.montant_paye
 * ─────────────────────────────────────────────────────────────*/

Pourquoi trois passes ?

  • A — normalement, chaque élève a une échéance par frais. On somme du - paye.
  • B — certains élèves n'ont pas d'échéance (frais créé après leur inscription). Sans repli, ils apparaîtraient comme « à jour » alors qu'ils doivent de l'argent.
  • C — des paiements globaux (sans echeance_id) ne sont pas reflétés dans Echeance.montant_paye. Il faut les imputer pour ne pas surestimer la dette.

🧠 Un indicateur faux est pire qu'un indicateur absent. Si le tableau de bord annonce 4 000 000 BIF de dette alors que la réalité est 6 000 000, le directeur prend de mauvaises décisions. Documentez toujours la méthode de calcul à l'écran (petit « i »).

17. Synchronisation « offline-first »

17.1 Le problème réel

Le bureau du complexe scolaire n'a pas toujours d'Internet. Pourtant, le caissier doit encaisser. Deux jours plus tard, il faut envoyer ces paiements dans le cloud pour que le coordonnateur les voie depuis son téléphone.

Contraintes :

  • écrire sans réseau (SQLite local) ;
  • ne rien perdre ;
  • éviter les doublons ;
  • gérer les conflits (même ligne modifiée des deux côtés) ;
  • respecter les dépendances (un paiement a besoin de son élève, qui a besoin de son établissement).

TableConfig { name: "EleveClasse", pk_cols: vec!["eleve_id", "classe_id"], …,
              fk_deps: vec![("eleve_id", "Eleve"), ("classe_id", "Classe")] },

TableConfig { name: "Paiement", pk_cols: vec!["id"], unique_cols: vec!["numero_recu"],
              fk_deps: vec![("eleve_id", "Eleve"), ("echeance_id", "Echeance"),
                            ("etablissement_id", "Etablissement"),
                            ("annee_scolaire_id", "AnneeScolaire"), ("user_id", "User")] },

Et l'ordre du tableau est l'ordre de synchronisation : parents d'abord. C'est pourquoi Etablissement vient avant User, qui vient avant Paiement.

🧠 L'ordre des dépendances est une information de conception, pas un détail d'implémentation. Il est aussi documenté dans SYNC_GUIDE.md.

17.4 Phase 1 — PULL (cloud → local)

Les suppressions

On ne peut pas deviner une suppression en lisant les lignes restantes. Le projet utilise donc l'AuditLog distant :

let url_del = format!("{}/rest/v1/AuditLog?action=eq.DELETE&created_at=gt.{}",
                      supabase_url, encode_param(&last_sync));

Toute ligne DELETE apparue côté cloud depuis la dernière synchronisation est appliquée localement (delete_composite_row).

Les données

Toute la table, par pages de 1 000 lignes, via l'en-tête Range de PostgREST :

let range_header = format!("{}-{}", offset, offset + page_size - 1);
let url = format!("{}/rest/v1/{}", supabase_url, t.name);

Puis :

for row in &remote_rows {
    if let Some(row_map) = row.as_object() {
        let _ = upsert_row(conn, t.name, &t.pk_cols, row_map);
    }
}

⚠️ Choix coûteux : rapatrier toute la table à chaque synchronisation ne passe pas l'échelle (imaginez 100 000 paiements). LAST_SYNC existe mais n'est pas utilisé pour filtrer le pull. Amélioration : ?updated_at=gt.<last_sync> — à condition que toutes les tables aient un updated_at fiable. Exercice 17.2.

Pendant le pull : les clés étrangères sont désactivées

let _ = conn.execute_batch("PRAGMA foreign_keys=OFF;");
// … tout le travail …
let _ = conn.execute_batch("PRAGMA foreign_keys=ON;");

Sinon, insérer un paiement avant son élève échouerait. C'est un compromis : on accepte temporairement des références orphelines, et des fonctions dédiées les réparent (repair_missing_remote_parents, filter_orphan_rows).

🧠 Désactiver une contrainte est toujours une dette. Notez-la, encadrez-la, et prévoyez un contrôle final (PRAGMA foreign_key_check).

17.5 Phase 2 — PUSH (local → cloud)

let push_batch_size = 25;
let on_conflict = format!("on_conflict={}", t.pk_cols.join(","));
let url = format!("{}/rest/v1/{}?{}", supabase_url, t.name, on_conflict);
let res = http_post_with_retry(&client, &url, &key, &format!("Bearer {}", key), &Value::Array(batch));
  • lots de 25 : compromis entre débit et taille de requête ;
  • on_conflict=id + en-tête Prefer: resolution=merge-duplicates = upsert ;
  • en cas d'échec, nouvelle tentative sur unique_cols (par exemple matricule) ;
  • retries exponentiels (500 ms, 1 s, 2 s, 4 s) sur 429 et 5xx.

Réparation des parents manquants

Si un paiement local référence un élève absent du cloud, la synchronisation échoue en violation de clé étrangère. Le moteur pousse alors le parent avant de réessayer (push_rows_with_dependencies) :

fn dependency_configs(table_name: &str) -> Vec<(&'static str, &'static str)> {
    match table_name {
        "Paiement" => vec![("eleve_id", "Eleve"), ("echeance_id", "Echeance"),
                           ("etablissement_id", "Etablissement"),
                           ("annee_scolaire_id", "AnneeScolaire"), ("user_id", "User")],
        …
    }
}

17.6 Les conflits

Le projet applique une politique simple : le dernier écrivain gagne, avec priorité au cloud pendant le pull (upsert), puis priorité au local pendant le push.

Conséquences :

  • une modification locale non poussée peut être écrasée par le pull ;
  • sur deux postes, une même école modifiée des deux côtés produit un résultat dépendant de l'ordre.

Politiques possibles :

PolitiqueAvantageRisque

🔧 Recommandation : ajouter une colonne version INTEGER (incrémentée à chaque écriture) et refuser un push si la version distante est plus récente. Journaliser le conflit et laisser l'utilisateur choisir.

18. Déboguer la synchronisation

La synchronisation est la partie du logiciel qui échoue le plus souvent — et la plus difficile à diagnostiquer, parce qu'elle mêle réseau, base locale, cloud, dépendances et droits. Ce chapitre est un manuel d'intervention, à garder ouvert.

18.1 La méthode en cinq minutes

1. Le statut      → Paramètres → Synchronisation → « Vérifier le statut »
2. La validation  → validate_sync_ready : quelles alertes ?
3. Le réseau      → la machine atteint-elle Supabase ?
4. La dernière erreur → logs (stderr) + message affiché
5. La donnée      → la ligne est-elle vraiment là, en local ? dans le cloud ?

🧠 Ne relancez jamais une synchronisation en boucle sans avoir lu l'erreur. Vous risquez de créer des doublons ou de saturer l'API (429).

18.6 Les incidents typiques

« Foreign key constraint violated »

Cause : une ligne enfant (Paiement) référence un parent (Eleve) absent du cloud.

Le moteur tente de pousser le parent (repair_missing_remote_parents). Si cela échoue :

-- identifier les orphelins locaux
SELECT p.id, p.eleve_id FROM Paiement p
LEFT JOIN Eleve e ON e.id = p.eleve_id WHERE e.id IS NULL;

Correction : soit créer/synchroniser l'élève, soit réaffecter le paiement, soit archiver la ligne.

« UNIQUE constraint failed: Paiement.numero_recu »

Cause : deux caisses ont produit le même numéro de reçu.

Vérifier :

SELECT numero_recu, COUNT(*) FROM Paiement GROUP BY numero_recu HAVING COUNT(*) > 1;

Correction : renommer le doublon local (avec audit) ou centraliser la numérotation.

« Sync réussie mais rien n'est poussé »

Trois causes possibles :

  1. LAST_SYNC est à jour et le pull ramène les mêmes lignes (normal) ;
  2. les lignes sont filtrées comme orphelines (filter_orphan_rows) ;
  3. les écritures ont eu lieu après le démarrage de la synchronisation.

Diagnostic :

SELECT cle, valeur FROM ConfigSysteme WHERE cle = 'LAST_SYNC';

et dans Supabase : SELECT count(*) FROM "Paiement";

« La synchronisation prend 10 minutes »

Le pull rapatrie toutes les tables, page par page. Avec 50 000 paiements, cela fait 50 requêtes rien que pour cette table. Solutions : filtre updated_at, index côté Supabase, et une politique de purge des vieilles années.

« Hors ligne — données en attente » persistant

L'indicateur (syncState === 'offline') reste affiché après une erreur. Vérifiez navigator.onLine, puis le statut réel. L'erreur est volontairement silencieuse côté interface : bonne idée pour ne pas inquiéter, mauvaise idée pour diagnostiquer.

18.7 Réinitialiser la synchronisation

Quand tout est bloqué et que vous avez une sauvegarde :

-- ⚠️ À faire uniquement sur une copie de sauvegarde
DELETE FROM ConfigSysteme WHERE cle = 'LAST_SYNC';

La prochaine synchronisation repart de 1970-01-01 : tout sera re-téléchargé et re-poussé. Sur une grosse base, prévoyez plusieurs minutes et surveillez les doublons.

⚠️ Avant toute manipulation :

sqlite3 ~/SGFS-ME/data/sgfs.db ".backup '/tmp/avant-reset.db'"

18.8 Un mode « simulation » utile

Pour tester sans réseau réel, ajoutez un drapeau dans ConfigSysteme :

let dry_run = conn.query_row(
    "SELECT valeur FROM ConfigSysteme WHERE cle = 'SYNC_DRY_RUN'", [],
    |r| r.get::<_, String>(0)).unwrap_or_else(|_| "false".into()) == "true";

Le moteur compte les lignes à envoyer sans les envoyer. Indispensable pour valider un correctif sur une base de production sans écrire dans le cloud.

19. Tests et qualité

19.1 Le constat honnête

Le dépôt ne contient aucun test automatisé. Pas de #[cfg(test)], pas de *.test.ts, pas de dossier e2e/. La commande bun run lint existe, mais elle ne vérifie ni les types ni le comportement.

Conséquence directe : chaque modification d'une commande Rust (par exemple create_paiement) nécessite un test manuel complet — et l'oubli d'un cas limite se paie en production.

Ce chapitre donne un plan de tests réaliste, réalisable en quelques heures, qui apporte 80 % de la valeur.

20.4 Les données de l'utilisateur et les mises à jour

C'est le point le plus critique d'une application de bureau : la base existe déjà chez le client, avec ses données. Une mise à jour ne doit jamais les perdre.

Installation 1.0 : SGFS-ME/data/sgfs.db (schéma v1)
Installation 1.1 : même chemin  →  il faut MIGRER, pas recréer

Le schéma actuel utilise CREATE TABLE IF NOT EXISTS : il ne modifie pas une table existante. Ajouter une colonne exige une migration explicite.

Patron de migration simple et sûr

pub fn run_migrations(conn: &Connection) -> Result<(), AppError> {
    conn.execute_batch(
        "CREATE TABLE IF NOT EXISTS Migration (
            version    INTEGER PRIMARY KEY,
            applied_at TEXT NOT NULL DEFAULT (datetime('now'))
        );")?;

    let current: i64 = conn.query_row(
        "SELECT COALESCE(MAX(version), 0) FROM Migration", [], |r| r.get(0))?;

    let migrations: &[(i64, &str)] = &[
        (1, "ALTER TABLE Depense ADD COLUMN justificatif_url TEXT;"),
        (2, "CREATE INDEX IF NOT EXISTS idx_paiement_mode ON Paiement(mode_paiement);"),
        (3, "ALTER TABLE User ADD COLUMN doit_changer_mdp INTEGER NOT NULL DEFAULT 0;"),
    ];

    for (version, sql) in migrations {
        if *version > current {
            conn.execute_batch("BEGIN;")?;
            match conn.execute_batch(sql) {
                Ok(_) => {
                    conn.execute("INSERT INTO Migration (version) VALUES (?1)", [version])?;
                    conn.execute_batch("COMMIT;")?;
                    eprintln!("[MIGRATION] v{} appliquée", version);
                }
                Err(e) => {
                    conn.execute_batch("ROLLBACK;")?;
                    return Err(AppError::Database(format!("Migration v{} échouée : {}", version, e)));
                }
            }
        }
    }
    Ok(())
}

Appel dans init_db(), juste après l'exécution du schéma de base.

🧠 Règle d'or : une migration est irréversible en production. Sauvegardez la base avant d'appliquer, et rendez la sauvegarde accessible à l'utilisateur.

20.5 Sauvegarde automatique

Intégrez une sauvegarde quotidienne dans l'application :

fn backup_db(conn: &Connection) -> Result<(), AppError> {
    let dir = std::path::Path::new(&crate::db::get_db_path())
        .parent().unwrap().join("backups");
    std::fs::create_dir_all(&dir).ok();
    let cible = dir.join(format!("sgfs-{}.db", chrono::Local::now().format("%Y%m%d")));
    conn.execute("VACUUM INTO ?1", [cible.to_string_lossy().to_string()])?;
    Ok(())
}

VACUUM INTO produit une copie cohérente même avec le WAL actif. Puis purgez les sauvegardes de plus de 30 jours.

⚠️ Une sauvegarde qui reste sur le même disque ne protège pas d'une panne matérielle. Proposez un export vers une clé USB ou le cloud.

21. Sécurité et permissions

Ce chapitre est une audition de sécurité du projet, avec les correctifs. Il est volontairement direct : les faiblesses décrites ici existent dans le code livré.

21.1 Le modèle d'authentification actuel

// auth.rs — login
let valid = bcrypt::verify(&req.password, &user.password_hash)?;
// …
Ok(api_response(Ok(LoginResponse {
    token: user.id.clone(),        // ⚠️ le « jeton » EST l'identifiant utilisateur
    user: info,
})))
// auth.rs — get_me
let user_res = conn.query_row("SELECT … FROM User WHERE id = ?1 AND actif = 1", params![token], …);
let user = match user_res {
    Ok(u) => u,
    Err(_) => conn.query_row(
        "SELECT … FROM User WHERE (username = ?1 OR role = 'COORDINATEUR' OR role = 'ADMIN')
         AND actif = 1 ORDER BY created_at ASC LIMIT 1", params![token], …)?,
};

Faiblesse critique

N'importe quelle chaîne présentée comme token :

  1. correspond à un id existant → session de cet utilisateur ;
  2. sinon, si elle vaut admin ou si un coordonnateur existe → session administrateur.

Autrement dit, un jeton arbitraire donne les pleins pouvoirs. Le localStorage du WebView suffit à déclencher cela.

Pourquoi ce code existe ? Il a été écrit pour « ne jamais bloquer l'utilisateur » après une migration de données. C'est une béquille de développement restée en production.

Correctif minimal, sans changer l'architecture

CREATE TABLE IF NOT EXISTS Session (
    token        TEXT PRIMARY KEY,
    user_id      TEXT NOT NULL,
    created_at   TEXT NOT NULL DEFAULT (datetime('now')),
    expires_at   TEXT NOT NULL,
    revoked      INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (user_id) REFERENCES User(id) ON DELETE CASCADE
);
#[tauri::command]
pub fn login(db: State<'_, DbConn>, req: LoginRequest) -> Result<Value, AppError> {
    let conn = db.lock()?;
    let (id, hash, actif) = conn.query_row(
        "SELECT id, password_hash, actif FROM User WHERE username = ?1",
        params![req.username], |r| Ok((r.get::<_, String>(0)?, r.get::<_, String>(1)?, r.get::<_, i64>(2)?)),
    ).map_err(|_| AppError::AuthFailed("Identifiants incorrects".into()))?;

    if actif == 0 { return Err(AppError::AuthFailed("Compte désactivé".into())) }
    if !bcrypt::verify(&req.password, &hash).map_err(|_| AppError::AuthFailed("Identifiants incorrects".into()))? {
        return Err(AppError::AuthFailed("Identifiants incorrects".into()));
    }

    let token = generate_session_token();          // 32 octets aléatoires, hex
    let expires = (chrono::Utc::now() + chrono::Duration::hours(12)).to_rfc3339();
    conn.execute("INSERT INTO Session (token, user_id, expires_at) VALUES (?1,?2,?3)",
                 params![token, id, expires])?;
    // … renvoyer token + infos
    Ok(api_response(Ok(LoginResponse { token, user: info })))
}

Et get_me doit vérifier :

SELECT u.* FROM Session s JOIN User u ON u.id = s.user_id
WHERE s.token = ?1 AND s.revoked = 0 AND s.expires_at > datetime('now') AND u.actif = 1;

Supprimez le repli (ORDER BY created_at ASC LIMIT 1). Un échec doit être un échec.

21.2 Les mots de passe

// db/mod.rs — seed_default_admin
let hash = bcrypt::hash("admin123", 4)?;    // ⚠️ coût 4 = très rapide à casser
  • coût 4 : environ 2^4 = 16 itérations. Un coût de 12 est aujourd'hui un minimum raisonnable (≈ 250 ms sur un poste courant).
  • mot de passe par défaut connu de tous : admin123.

Correctif :

let hash = bcrypt::hash("admin123", 12)?;
// et en base
conn.execute("UPDATE User SET doit_changer_mdp = 1 WHERE username = 'admin'", [])?;

Au login, si doit_changer_mdp = 1, forcer un écran de changement avant tout accès.

🧠 Ne testez jamais la sécurité avec des mots de passe réels de production. Créez un compte de test dédié.

21.3 L'autorisation : le trou le plus large

Une commande Rust ne sait pas qui l'appelle :

#[tauri::command]
pub fn delete_utilisateur(db: State<'_, DbConn>, id: String) -> Result<Value, AppError> {
    // aucun contrôle de rôle
}

Toute personne devant l'ordinateur, ou tout script injecté dans la WebView, peut l'appeler.

Trois niveaux de défense

  1. front : masquer les menus (déjà fait dans Sidebar.tsx) — confort, pas sécurité ;
  2. commande : vérifier le rôle avant l'action ;
  3. base : contraintes et triggers pour les règles invariantes.

Implémentation pragmatique d'un contexte de session côté Rust :

pub struct SessionCourante(pub std::sync::Mutex<Option<String>>); // user_id

pub fn exiger_coordinateur(db: &Connection, user_id: &str) -> Result<(), AppError> {
    let role: String = db.query_row(
        "SELECT role FROM User WHERE id = ?1 AND actif = 1", [user_id], |r| r.get(0),
    ).map_err(|_| AppError::AuthFailed("Session expirée".into()))?;
    if !matches!(role.to_uppercase().as_str(), "COORDINATEUR" | "ADMIN" | "SUPERADMIN") {
        return Err(AppError::AuthFailed(
            "Action réservée au coordonnateur.".into()));
    }
    Ok(())
}

Chaque commande sensible prend user_id (ou lit le jeton dans l'état géré) et appelle exiger_coordinateur.

🧠 Défense en profondeur : trois barrières valent mieux qu'une. Mais la seule qui compte vraiment est celle du back-end.

21.4 isCoordinateur : le défaut permissif

export function isCoordinateur(role: string | null | undefined): boolean {
  if (!role) return true      // ⚠️ aucun rôle ⇒ tous les droits
  // …
}

« Fail-open ». Correction :

export function isCoordinateur(role?: string | null): boolean {
  if (!role) return false
  const r = role.trim().toUpperCase()
  return ['COORDINATEUR', 'ADMIN', 'SUPERADMIN', 'ADMINISTRATEUR', 'COORD'].includes(r)
}

Vérifiez ensuite chaque écran : un utilisateur sans rôle ne doit plus rien voir.

Chapitre 1

Chapitre 2

2.1 — Hash bcrypt. Un hash bcrypt fait 60 caractères et commence par $2b$04$… : 04 est le coût. Le coût 4 (celui du seed) est très faible ; un coût 12 est recommandé. Le hash ne contient pas le mot de passe, mais son empreinte salée : deux utilisateurs avec le même mot de passe ont des hash différents.

2.2 — seed_default_admin. Le test SELECT COUNT(*) FROM User évite de créer un second administrateur à chaque démarrage. Sans lui, chaque lancement ajouterait admin… et échouerait de toute façon sur la contrainte UNIQUE(username), bloquant l'application au démarrage.

Chapitre 3

3.1 — Paiement partiel. Insertion dans Paiement (montant=100000, montant_affecte=100000, annule=0) et UPDATE Echeance SET montant_paye = 100000. L'écran affiche PARTIELLEMENT_PAYE, reste 50 000. L'annulation met annule=1, crée une AnnulationRecu avec motif et ramène montant_paye à 0 (MAX(0, …)), de sorte que l'échéance redevient EN_ATTENTE.

3.2 — Paiement multi-devises. Champs à renseigner : montant=72500, devise='BIF', montant_affecte=25, devise_echeance='USD', taux_change=2900, montant_original=25. Le frais reste libellé en USD ; l'échéance augmente de 25 USD ; la caisse enregistre 72 500 BIF.

pub fn create_echeances_bulk(db: State<'_, DbConn>, frais_scolaire_id: String,
                             annee_scolaire_id: String, eleve_ids: Vec<String>) -> Result<Value, AppError> {
    let mut conn = db.lock()?;
    let tx = conn.transaction()?;
    let mut crees = 0usize;

    let (montant, devise, etab, date_ech): (f64, String, String, Option<String>) = tx.query_row(
        "SELECT montant, devise, etablissement_id, date_echeance FROM FraisScolaire WHERE id = ?1",

             (id, eleve_id, frais_scolaire_id, etablissement_id, annee_scolaire_id,
              montant_du, montant_paye, statut, date_echeance, created_at, updated_at)
